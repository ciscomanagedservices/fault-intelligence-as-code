## Assumptions Made During Generation

| # | Assumption | Rationale |
|---|---|---|
| 1 | **IPv4 unicast address-family throughout** | The example syslog and research do not specify an address family; IPv4 unicast is the overwhelmingly common case for this fault. IPv6 unicast and VPNv4 variants exist — a SME should confirm if those address families need explicit coverage. |
| 2 | **Severity = WARNING** | The workspace default is WARNING. The session does go down (potential traffic impact), which might warrant MAJOR in some governance frameworks. Flagged for SME review. |
| 3 | **`clear bgp ipv4 unicast {{ neighbor_ip }}`** | The address-family-explicit form is used for clarity. The simpler `clear bgp {{ neighbor_ip }}` also works and clears all address families — SME may prefer that form. |
| 4 | **`rollback configuration last 1` rolls back exactly one commit** | This guide assumes the offending change is the most recent commit. If the problematic change is two or more commits back, the operator must use `rollback configuration last N` or `rollback configuration to <CommitId>` to target the correct point. The guide's decision point in Step 2 calls this out. |
| 5 | **Rollback creates a new commit — no separate `commit` needed** | In IOS XR, `rollback configuration` automatically generates a new commit. No manual `commit` is required after the rollback command. |
| 6 | **Session does not auto-recover** | The session remains Idle until `clear bgp` is executed. If the neighbor has `restart` configured on their side, the session may auto-recover after the rollback — this does not change the diagnostic steps. |
| 7 | **No VRF isolation** | The syslog shows `VRF: default`. Non-default VRF variants are noted in parenthetical commands in Steps 2 and 4. If the customer's environment uses non-default VRFs extensively, the RG may need expansion. |
| 8 | **Guide scope is config-change root cause only** | This redesign specifically targets faults caused by a recent route-policy or prefix-set change. Faults caused by routing table growth, redistribution changes, or new peers without a config change are out of scope and are handled via the Escalation section. |

## Open Items for SME Review

1. **Address-family scope** — Should the guide explicitly cover IPv6 unicast and VPNv4 variants? Commands differ (`show bgp ipv6 unicast neighbors ...`, `clear bgp vrf {{ vrf_name }} ipv6 unicast ...`).
2. **Severity** — WARNING or MAJOR? If this neighbor is a primary transit or only BGP upstream, the traffic impact is significant enough for MAJOR.
3. **Multi-commit rollback** — The guide shows `rollback configuration last 1`. Should Step 3 include guidance on targeting a specific CommitId (e.g., `rollback configuration to 1000000046`) for cases where the offending change is not the most recent commit?
4. **Rollback scope caution** — The caution notes that `rollback last 1` may reverse unrelated changes in the same commit. Should the guide include a step to manually edit only the route-policy as an alternative to rollback when the commit is mixed?
5. **Demo environment prefix counts** — The RG uses `3820` (healthy) and `8520` (fault) as sample prefix counts. If the demo environment uses much smaller prefix counts, the sample outputs should be adjusted for realism.
6. **Recurring fault prevention** — After the rollback, should the guide recommend a change-control review to prevent the policy from being re-applied? This could be a note at the end of Post-Repair Verification.
